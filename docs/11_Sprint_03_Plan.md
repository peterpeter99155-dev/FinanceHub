**1.1（2026-07-28）** 依開工前的計畫審查修正。原版本有四處實質缺陷與兩處過度僵化的規格：

- **「主密碼不跨 IPC」字面上不可實作。** 解鎖畫面在 renderer、資料庫在 main，密碼必然要跨一次 IPC。已改為「單次一次性傳遞，不得回傳、保存或再轉送；導出金鑰不得跨 IPC」。
- **「可靠區分錯密碼與檔案損壞」以目前設計做不到。** 錯誤金鑰會使檔頭看起來像損壞。已新增 key verifier 機制（S3-12）。

- **原備份說明會造成資料遺失。** WAL 模式下最近資料可能只存在 `-wal` 檔案，只複製主檔會遺失。已改為必須關閉程式後複製，且含 sidecar（S3-31）。
- **KDF 參數改為版本化。** 原版本要求參數永久不變，代價是永遠無法隨硬體提升成本。改為每個資料庫記錄其建立時的 KDF 版本並永遠沿用。
- **禁止後門改以結構測試強制。** 原版本僅要求字串掃描，那只能當輔助防線。改為「解鎖前不建立任何財務 Repository、Service 與 IPC handler」。

**1.0（2026-07-28）** 初版。

## Sprint Goal

打開「可以放真實財務資料」這道閘門。

```text
首次啟動 → 設定主密碼 → 建立加密資料庫與 metadata
後續啟動 → 輸入主密碼 → 驗證 → 解開資料庫 → 正常使用
密碼錯誤 → 明確告知，不進入主畫面，不改動任何資料
```

在此之前，`02_Requirements.md` 第 481 行的限制持續有效：**只能使用假資料**。本 Sprint 完成後該限制解除。

## 為什麼這個 Sprint 優先於功能

目前 `financehub.dev.db` 是明文檔案。任何人拿到它，用免費的 SQLite 檢視器就能讀完全部財務資料。

在加密完成前：

- 你不敢放真實數字，所以這個工具對你還沒有實際用處。
- 不能給任何人使用，因為風險由使用者承擔而抱怨會回到你身上。
- 手機版無法規劃，因為同步的檔案格式必須先確定。

## 已確認的決議

- **每次開啟都要輸入主密碼。** 不提供「記住此裝置」，導出金鑰完全不落地。
- **最小長度 8 字元**，不做複雜度強制。
- **範圍限定最小可用**：加密、首次設定、解鎖。閒置自動鎖定、改密碼、匯出功能排後續 Sprint。
- **備份初期不寫程式**，但必須在 README 寫出正確程序（見 S3-31）。

# 階段 0　技術可行性驗證

**這一階段不寫任何加密邏輯。目的只有一個：確認換掉資料庫套件之後，這個專案還能跑、還能打包、安裝後還能啟動。**

## S3-00　換掉資料庫套件（不啟用加密）

### 背景

目前使用 Node 內建的 `node:sqlite`（`DatabaseSync`），零相依、不需編譯，**但不支援加密**。

建議改用 `better-sqlite3-multiple-ciphers`。理由：直接整合 SQLCipher 在 Electron 上的難度極高，而 `@journeyapps/sqlcipher` 已無維護。

### 已知陷阱（開工前務必逐項確認）

1. **ABI 不相容。** Electron 的 Node ABI 與一般 Node.js 不同。針對本機 Node 編譯的 `.node` 會出現 `NODE_MODULE_VERSION` 不符或 `Module did not self-register`。Forge 會自動 rebuild，但必須驗證實際輸出。
2. **不應假設有 Electron 43 的 prebuild。** 沒有時會退回本機編譯，需要上述工具鏈。
3. **Windows delay-load hook。** `win_delay_load_hook` 必須正確啟用並連到 Electron 的 `node.lib`，否則 packaged app 可能出現找不到 procedure 或無法載入 DLL。
4. **ASAR 解包。** `.node` 不能只留在 ASAR 虛擬路徑。專案已有 `AutoUnpackNativesPlugin`，但必須**實際檢查 `app.asar.unpacked` 裡真的有 binary**，且 binding resolver 找得到。
5. **Webpack 處理方式。** 原生模組不能被當普通 JS bundle。要確認 main bundle 從正確實體位置載入 `.node`，而不是指向 ASAR 內部或開發機路徑。
6. **架構一致。** x64 package 必須用 x64 binary。
7. **版本鎖定。** `better-sqlite3-multiple-ciphers`、底層 SQLite3MultipleCiphers 與 Electron 任一升級都可能要求重新編譯。相依版本必須鎖定精確版本，不得使用浮動範圍。

### 做法

- 只替換資料庫存取套件，**不啟用任何加密**。
- API 差異只在 infrastructure 層吸收。
- **domain、application、renderer 一行都不准改。** 若因型別或 import 洩漏被迫修改上層，停止並回報 —— 那代表分層有洩漏，要先處理。

### 關於測試的明確界線

換套件後，infrastructure 測試建立資料庫的方式與型別**必然要改**，這是允許的。

**禁止的是：**

- 修改測試的**斷言內容**
- 刪除或跳過測試
- 放寬驗收標準

若發現必須修改斷言，停止並回報 —— 那代表行為真的變了，不是 API 差異。

### 驗收方式（全部必須通過）

- `npm.cmd run typecheck`
- `npm.cmd run lint`
- `npm.cmd test` —— 99 項全綠
- `npm.cmd run test:e2e` —— 5 項全綠
- `npm.cmd run test:package-smoke`
- `npm.cmd run test:electron` —— 連續 10 次全綠
- `npm.cmd run make` —— 能產出 `.exe` 安裝檔
- **安裝檔實際安裝並啟動一次**，確認原生模組在打包後的環境能載入
- **確認 `app.asar.unpacked` 內確實包含 `.node` binary**

倒數兩項最重要。原生模組最常見的失敗是「開發環境正常、打包後載不到」。

安裝驗證需要 Windows GUI，可能遇到 SmartScreen、防毒軟體或舊版本占用，無法只靠自動化完成，本機手動執行即可。

### 停止條件

**若上述任一項無法通過且無法在合理成本內解決，停止本 Sprint 並回報。** 不要為了繼續而降低驗收標準，也不要移除測試。

替換失敗的話，加密方案需要重新評估（例如改為檔案層加密），那是另一個規劃。

### 不要做

- 不要同時啟用加密。
- 不要順手升級其他套件。

# 階段 1　加密格式與金鑰

## S3-10　定義加密格式（先寫規格，再寫程式）

### 為什麼要先定格式

加密格式一旦有資料寫入就綁死了。格式定義不完整的話，未來升級套件或調整參數都可能讓既有資料庫永久打不開。

**本項必須先產出書面規格並記入 `04_Decision_Log.md`，才開始實作。**

### 必須明確記錄的項目

| 項目 | 說明 |
|---|---|
| **格式版本** | 整個加密格式的版本號。未來任何結構變更都遞增。 |
| **KDF 版本** | 金鑰導出的參數組版本。**每個資料庫永遠使用其建立時記錄的版本。** |
| **KDF 參數** | `scrypt` 的 `N`、`r`、`p`、`keyLength`、`maxmem`，全部明確指定，不用套件預設。 |
| **salt** | 每個資料庫獨立隨機產生，至少 16 bytes。 |
| **cipher 名稱與參數** | 明確指定，**不得依賴套件的預設 cipher** —— 套件升級可能改變預設行為。 |
| **cipher page size** | 明確指定。 |
| **密碼編碼規則** | UTF-8，並指定 Unicode 正規化形式（建議 NFC）。 |

### 關於 KDF 版本化

原計畫要求「參數永久不變」，代價是永遠無法隨硬體提升成本。正確設計是：

- 每個資料庫的 metadata 記錄它使用的 KDF 版本。
- 開啟時讀取該版本，用對應參數導出金鑰。
- **既有資料庫永遠使用建立時的版本，不得偷偷改用新參數。**
- 未來要提升成本，是新增 KDF 版本，舊資料庫不受影響。

### 密碼編碼必須釘死

視覺上相同的字串可能有不同的 byte 序列（NFC 與 NFD）。若設定時與解鎖時的正規化方式不一致，**同一個密碼會導出不同金鑰，使用者會被鎖在門外**。

規則：

- 一律 UTF-8。
- 一律套用指定的 Unicode 正規化形式。
- **不得自動 trim 前後空白** —— 空白可能是密碼的一部分。
- 設定長度上限（建議 1024 字元），避免極端輸入耗盡資源。「不設限制」至少要有技術上限。

### 依第 13 節建立機械化強制

- 測試釘住 KDF 參數與格式版本：給定已知密碼與已知 salt，導出結果必須等於已知期望值。
- 註解明確說明：**改動這些值等於讓對應版本的既有資料庫無法開啟。**

## S3-11　Metadata sidecar

### 為什麼需要

**salt 必須在開啟加密資料庫之前取得**，因此不能存放在加密資料庫內部。

### 做法

- 建立獨立的 metadata 檔案（sidecar），與資料庫放在同一目錄。
- 內容：格式版本、KDF 版本、salt、cipher 參數、key verifier（見 S3-12）。
- **salt 與這些 metadata 明文保存是設計的一部分**，不是缺陷。它們不足以推導金鑰。
- 寫入必須是原子操作（先寫暫存檔再改名），避免中途斷電產生半寫入的檔案。

### 必須處理的失敗情境

| 情境 | 要求行為 |
|---|---|
| 資料庫存在、sidecar 不見 | **明確報錯並停止。絕對不得誤判為首次啟動而覆寫資料。** |
| sidecar 存在、資料庫不見 | 明確報錯並停止，提示可能是備份不完整。 |
| 首次設定中途斷電 | 下次啟動能辨識為未完成狀態，不得留下半加密或無法開啟的資料。 |
| sidecar 格式版本高於程式支援 | 明確報錯，提示需要更新程式，不得嘗試強行開啟。 |

第一項是**資料遺失級的風險**，必須有測試涵蓋。

## S3-12　Key verifier 與錯誤區分

### 問題

加密 SQLite 對「金鑰錯誤」與「檔頭／page／schema 損壞」常回傳相同或近似的錯誤。原計畫要求「可靠區分錯密碼與檔案損壞」，以目前設計做不到。

### 做法

- 從主密碼另外導出一把**獨立子金鑰**，計算一個 verifier（HMAC 或等效機制），存入 sidecar。
- 解鎖流程：
  1. 讀 sidecar 取得 salt 與 KDF 版本。
  2. 導出金鑰與子金鑰。
  3. 比對 verifier。**不符 → 密碼錯誤。**
  4. 符合但資料庫仍打不開 → **檔案損壞或無法讀取。**

### 安全性說明

verifier 提供了離線驗證密碼的能力。但攻擊者取得加密資料庫後，本來就能離線無限次嘗試 —— **威脅模型沒有實質改變**，而使用者得到的是可判斷的錯誤訊息。

依 `00_Architecture_Rules.md` 第 2 節，兩種情況各有穩定錯誤代碼與中文文案。

### 若不採用 verifier

則必須把文案合併為「主密碼錯誤或資料庫無法讀取」，**不得承諾可靠分類**。

## S3-13　以金鑰開啟資料庫

### 做法

- 資料庫檔名改為 `financehub.db`。舊的 `financehub.dev.db` 不讀取、不刪除、不轉換（見 S3-30）。
- 開啟流程：讀 sidecar → 導出金鑰 → 驗證 verifier → 套用金鑰 → 執行 migration。
- 交易邊界、migration 機制、repository 介面**全部不變**。Sprint 2.5 已整理乾淨，加密只影響「怎麼開啟」。

### 錯誤密碼絕對不得改動資料

解鎖失敗時**禁止**：

- 執行任何 migration
- 建立空 schema
- 重寫檔頭
- truncate 或覆蓋原檔

必須有測試：用錯誤密碼嘗試開啟後，資料庫與 sidecar 的內容與修改時間皆未變動。

**理由：** 打錯一次密碼就毀掉資料庫，是不可接受的失敗模式。

## S3-14　WAL、SHM 與明文洩漏檢查

### 必須實測

SQLite 在 WAL 模式下會產生 `-wal` 與 `-shm` 檔案。**必須實際確認這些檔案不含明文財務資料。**

檢查方式：建立含已知字串（例如帳戶名稱「示範銀行存款」）的加密資料庫，然後在 `financehub.db`、`-wal`、`-shm` 以及任何 journal 檔案中搜尋該字串的明文，**必須全部找不到**。

回報必須附上實際檢查方式與結果。

### 完整性保護

「外部 SQLite 工具讀不到」只證明它不是普通 SQLite 檔案，**不證明密文有完整性保護**。

必須確認所選 cipher 是否提供 page 層級的驗證（authentication／HMAC），以及資料損壞時的實際行為。結果記入 Decision Log。

## S3-15　金鑰與密碼的處理規則

### IPC 邊界（v1.1 修正）

解鎖畫面在 renderer、資料庫在 main，因此**主密碼必然要跨一次 IPC**。原計畫的「主密碼不跨 IPC」不可實作。

修正後的規則：

- 主密碼**只允許透過單一、一次性的解鎖 IPC** 由 renderer 傳至 main。
- 該 IPC **不得回傳密碼**、不得保存、不得寫入 log、不得再轉送給任何其他模組。
- **導出金鑰不得跨 IPC**，只存在 main process。

### 記憶體處理（誠實的界線）

- 導出金鑰的 Buffer 在套用後盡力清零（best-effort）。
- **JavaScript 字串無法可靠清零。** 「導出後即丟棄」只能表示移除應用程式的引用，不能保證作業系統 swap、crash dump 或原生函式庫內部副本不存在該資料。
- 這是平台限制，**必須在 Decision Log 誠實記錄，不得聲稱做到了無法保證的事**。

### 一律禁止

- 金鑰或密碼寫入任何檔案、log、錯誤訊息、IPC 回傳值。
- crash log 或診斷輸出包含解鎖參數。

## S3-16　絕對禁止跳過解鎖的路徑

**不得提供任何跳過解鎖的機制。** 包含但不限於：環境變數開關、預設密碼、命令列參數、開發模式自動解鎖、test-only unlock adapter 被 production bundle 引用。

理由：這類後門一定會留在正式版本裡，是資安事故最常見的單一成因。

### 強制方式（v1.1 改為結構測試）

字串掃描只能當輔助防線，無法證明沒有後門。**必須改用結構性保證：**

- **解鎖成功前不建立**任何財務 Repository、Service 與財務相關 IPC handler。
- 所有資料庫開啟路徑都必須持有「解鎖成功後才產生」的能力物件或狀態，無法憑空取得。
- **測試：解鎖前呼叫任何財務 IPC 必須失敗。**
- **測試：production bundle 不含測試密碼或 test-only 解鎖路徑。**

測試可以使用明確的假密碼，但只能存在測試程式中，不得被 production bundle 引用。

# 階段 2　解鎖流程

## S3-20　首次啟動：設定主密碼

### 做法

- 偵測到沒有既有資料庫**且沒有 sidecar** 時，才進入設定流程。任一存在但另一缺失，依 S3-11 報錯。
- 需輸入兩次確認一致。
- **最小長度 8 字元**（已確認）。上限 1024 字元。
- **不做複雜度強制** —— 不要求大小寫、數字或符號。強制複雜度已被證實會讓使用者選出更弱且更難記的密碼（例如 `Password1!` 這類固定模式），長度才是真正有效的因素。
- 最小長度必須定義為集中常數並記入 `04_Decision_Log.md`。

  **理由：** 未來若調高最小長度，既有使用者的較短密碼會無法通過驗證，等於把他們鎖在門外。要改必須先設計過渡方式，因此這個數字屬於決策層級。

- **必須顯示明確警告**，使用者要主動確認才能繼續：

  > 忘記主密碼將無法復原任何資料。沒有重設信件，沒有客服可以協助 —— 因為金鑰只有你持有。
  > 請確認你能記得這個密碼，並依 README 說明定期備份資料庫與 metadata 檔案。

### 驗收方式

- 兩次輸入不一致時不得建立資料庫或 sidecar。
- 未確認警告不得繼續。
- 設定完成後直接進入主畫面。
- 建立過程中斷（模擬）不得留下無法開啟的半成品。

## S3-21　後續啟動：解鎖畫面

### 做法

- 偵測到既有資料庫與 sidecar 時顯示解鎖畫面。
- 焦點自動落在密碼欄位。**依第 6.1 節，不得使用 `setTimeout` 設定焦點，一律用 `useLayoutEffect`。**
- Enter 可送出。支援貼上。
- **解鎖前不得載入或顯示任何財務資料。**

### 輸入語義

- 不得自動 trim 前後空白。
- 依 S3-10 的正規化規則處理輸入。
- 輸入法組字中不得誤送出。

### 驗收方式

- **依第 9.2 節，測試必須斷言「解鎖前畫面不存在任何財務數字、帳戶名稱或交易資料」**，不只斷言解鎖後能進入。
- 密碼錯誤後可重試，不需重啟程式。
- 密碼錯誤後資料庫與 sidecar 未被改動（與 S3-13 的測試呼應）。

## S3-22　關閉與清理

- 關閉視窗或退出程式時，資料庫連線必須確實關閉。
- 密碼引用盡早釋放。
- 導出金鑰的 Buffer 盡力清零。
- 確認 crash log 不含解鎖參數。

# 階段 3　資料與文件

## S3-30　既有開發資料庫

### 做法

- 舊的 `financehub.dev.db` 內容全部是假資料，**不寫轉換 migration**。
- 新資料庫使用新檔名 `financehub.db` 加上 sidecar。
- 舊檔案保留不動、不讀取。README 說明使用者可自行手動刪除。

### 為什麼不寫轉換

那個 migration 只會在你自己的電腦上執行一次，之後永不再用，卻要承擔測試與維護成本。既有資料全是假的，重建更乾淨。

**此決定必須記入 `04_Decision_Log.md`**，因為未來若有人拿舊版資料庫升級，需要知道當初是這樣處理的。

## S3-31　加密相容性 fixture

在 repo 中保留一個**固定的、內容完全是假資料的加密資料庫與 sidecar**，作為未來升級的相容性測試基準。

用途：`better-sqlite3-multiple-ciphers`、底層 SQLite3MultipleCiphers 或 cipher 版本升級時，必須先用這個 fixture 驗證**舊資料庫仍可讀取**，才能升級。

密碼固定且寫在測試程式中。此 fixture 不含任何真實資料，可安全提交 Git。

## S3-32　更新 README（備份程序已修正）

### 必須新增

**主密碼**

- 意義與遺失後果：無法復原，沒有重設機制。

**備份程序（v1.1 修正，原版本會造成資料遺失）**

原計畫寫「直接複製 `financehub.db`」。**這是錯的** —— WAL 模式下最近的資料可能只存在 `-wal` 檔案中，只複製主檔會遺失資料。

正確程序必須寫明：

1. **完全關閉 FinanceHub**（不是只關視窗，要確認程式已結束）。
2. 複製 **`financehub.db` 與 metadata sidecar 兩個檔案**。缺任何一個都無法還原。
3. 可放隨身碟或雲端硬碟 —— 資料庫已加密，只有你的主密碼能開。
4. 還原時兩個檔案要放回同一目錄。

同時說明檔案的實際位置。

**其他**

- 加密完成後「只能使用假資料」的限制已解除。
- 同步更新 `02_Requirements.md` 第 481 行的狀態。
