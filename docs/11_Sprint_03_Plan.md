## Sprint Goal

打開「可以放真實財務資料」這道閘門。

```text
首次啟動 → 設定主密碼 → 資料庫以該密碼加密
後續啟動 → 輸入主密碼 → 解開資料庫 → 正常使用
密碼錯誤 → 明確告知，不進入主畫面
```

在此之前，`02_Requirements.md` 第 481 行的限制持續有效：**只能使用假資料**。本 Sprint 完成後該限制解除。

## 為什麼這個 Sprint 優先於功能

目前 `financehub.dev.db` 是明文檔案。任何人拿到它，用免費的 SQLite 檢視器就能讀完全部財務資料，不需要密碼。

在加密完成前：

- 你不敢放真實數字，所以這個工具對你還沒有實際用處。
- 不能給任何人使用，因為風險由使用者承擔而抱怨會回到你身上。
- 手機版無法規劃，因為同步的檔案格式必須先確定。

**功能再多，閘門沒開都用不上。**

## 已由文件確定、不重新討論的

- **秘密不得明文保存、寫入程式碼或提交 Git**（第 488 行）
- **儲存層必須預留加密設計**（第 481 行）

## 本 Sprint 的決議

- **每次開啟都要輸入主密碼。** 不提供「記住此裝置」，金鑰完全不落地。別人拿到你的電腦（包含已登入的 Windows）也開不了。
- **範圍限定最小可用**：加密、首次設定、解鎖。閒置自動鎖定、改密碼、匯出功能都排後續 Sprint。
- **備份初期不寫程式。** 加密後備份就是複製那個檔案，寫進 README 即可。

# 階段 0　技術可行性驗證

**這一階段不寫任何加密邏輯。目的只有一個：確認換掉資料庫套件之後，這個專案還能跑、還能打包。**

## S3-00　換掉資料庫套件（不啟用加密）

### 背景

目前使用 Node 內建的 `node:sqlite`（`DatabaseSync`），零相依、不需編譯。**它不支援加密。**

建議改用 `better-sqlite3-multiple-ciphers`。理由：直接整合 SQLCipher 在 Electron 上的難度極高，而 `@journeyapps/sqlcipher` 已無維護。

### 這一步的風險

它是**原生模組**，需要針對 Electron 版本編譯。可能影響：

- `npm run package` 與 `npm run make`
- 15 個測試檔、99 項測試（全部走資料庫）
- Electron 啟動

`forge.config.ts` 已有 `AutoUnpackNativesPlugin`，是為原生模組準備的，但仍需實測。

### 做法

- 只替換資料庫存取套件，**不啟用任何加密**。
- API 差異（`DatabaseSync` 與 `better-sqlite3` 的介面不同）只在 infrastructure 層吸收。
- **domain、application、renderer 一行都不准改。** 若發現必須改，停止並回報 —— 那代表分層有問題，要先處理。

### 驗收方式（全部必須通過）

- `npm.cmd run typecheck`
- `npm.cmd run lint`
- `npm.cmd test` —— 99 項全綠
- `npm.cmd run test:e2e` —— 5 項全綠
- `npm.cmd run test:package-smoke`
- `npm.cmd run test:electron` —— 連續 10 次全綠
- `npm.cmd run make` —— 能產出 `.exe` 安裝檔
- **安裝檔實際安裝並啟動一次**，確認原生模組在打包後的環境能載入

最後一項最重要。原生模組最常見的失敗是「開發環境正常、打包後載不到」。

### 停止條件

**若上述任一項無法通過且無法在合理成本內解決，停止本 Sprint 並回報。** 不要為了繼續而降低驗收標準，也不要移除測試。

替換資料庫套件失敗的話，加密方案需要重新評估（例如改為檔案層加密），那是另一個規劃。

### 不要做

- 不要同時啟用加密。
- 不要順手升級其他套件。
- 不要修改測試來配合新套件的行為差異。若行為真的不同，回報後再決定。

# 階段 1　加密與金鑰

## S3-10　主密碼導出金鑰

### 做法

- 使用 Node 內建 `crypto.scrypt`。選它的理由：不需要新增相依套件，而本 Sprint 已經加了一個原生模組，不宜再加。
- 每個資料庫產生獨立的隨機 salt，長度至少 16 bytes。
- **金鑰導出參數必須集中定義為常數，並寫進 `04_Decision_Log.md`。**

### 為什麼參數必須釘死

改動 scrypt 的參數（cost、blockSize、parallelization）會導致**同一個密碼算出不同的金鑰**，結果是所有既有資料庫全部開不了。這是不可逆的資料遺失。

依 `00_Architecture_Rules.md` 第 13 節（規範必須盡可能機械化），本項必須建立測試釘住參數：

```ts
// 概念示意
expect(KEY_DERIVATION_PARAMS).toEqual({ ... });
expect(deriveKey('known-password', knownSalt)).toBe('known-expected-key');
```

任何人改動參數，測試立刻紅，並且註解要說明「改這個等於讓所有既有資料庫失效」。

### 金鑰處理規則

- 金鑰只存在記憶體，**不得寫入任何檔案、log、錯誤訊息或 IPC 回傳值**。
- 主密碼本身不得保存，導出金鑰後即丟棄。
- salt 可以明文保存（那是它的設計用途）。

## S3-11　以金鑰開啟資料庫

### 做法

- 資料庫檔名改為 `financehub.db`。**舊的 `financehub.dev.db` 不讀取、不刪除、不轉換**（見 S3-30）。
- 開啟流程：導出金鑰 → 套用金鑰 → 驗證能否讀取 → 執行 migration。
- 交易邊界、migration 機制、repository 介面**全部不變**。這一層在 Sprint 2.5 已經整理乾淨，加密只影響「怎麼開啟」。

### 驗收方式

- 用正確密碼開啟後，所有既有功能行為不變。
- **用任何 SQLite 檢視器直接打開 `financehub.db`，必須無法讀取內容。** 這一項要實際做並在回報中說明結果。
- 15 個測試檔、99 項測試在加密資料庫上全部通過。

## S3-12　錯誤密碼處理

### 做法

- 密碼錯誤時明確告知「主密碼錯誤」，不進入主畫面。
- **應區分「密碼錯誤」與「檔案損壞或無法讀取」兩種情況。**

### 為什麼要區分

一般安全建議是「不要洩漏失敗原因」，但那是針對線上服務的暴力破解。這是本機單機應用，攻擊者已經拿到檔案，可以離線無限次嘗試 —— 隱藏原因對他毫無阻礙，卻會讓真正的使用者在檔案損壞時完全無法判斷發生什麼事。

依 `00_Architecture_Rules.md` 第 2 節，兩種情況各有穩定錯誤代碼與中文文案。

### 絕對禁止

**不得提供任何跳過解鎖的路徑。** 包含但不限於：

- 環境變數開關（`SKIP_UNLOCK`、`DEV_MODE` 之類）
- 預設密碼
- 命令列參數
- 開發模式自動解鎖

理由：這類後門一定會留在正式版本裡。這是資安事故最常見的單一成因。

依第 13 節建立測試掃描原始碼，禁止出現這類模式。測試必須涵蓋 `src/main.ts`、`src/preload.ts` 與資料庫開啟路徑。

# 階段 2　解鎖流程

## S3-20　首次啟動：設定主密碼

### 做法

- 偵測到沒有既有加密資料庫時，進入「設定主密碼」流程。
- 需輸入兩次確認一致。
- 最小長度限制（建議 8 字元，但由你確認）。不做複雜度強制 —— 強制符號與大小寫已被證實會讓使用者選出更弱且更難記的密碼。
- **必須顯示明確警告**，且使用者要主動確認才能繼續：

  > 忘記主密碼將無法復原任何資料。沒有重設信件，沒有客服可以協助 —— 因為金鑰只有你持有。
  > 請確認你能記得這個密碼，並依 README 說明定期備份資料庫檔案。

### 驗收方式

- 兩次輸入不一致時不得建立資料庫。
- 未確認警告不得繼續。
- 設定完成後直接進入主畫面，不需再輸入一次。

## S3-21　後續啟動：解鎖畫面

### 做法

- 偵測到既有加密資料庫時顯示解鎖畫面。
- 焦點自動落在密碼欄位。**依第 6.1 節，不得使用 `setTimeout` 設定焦點。**
- Enter 可送出。
- 解鎖前不得載入或顯示任何財務資料。

### 驗收方式

- 解鎖前的畫面不含任何金額、帳戶名稱或交易資料。
- 密碼錯誤後可重試，不需重啟程式。
- 依第 9.2 節，測試必須斷言「解鎖前畫面不存在任何財務數字」，不只斷言解鎖後能進入。

# 階段 3　資料與文件

## S3-30　既有開發資料庫

### 做法

- 舊的 `financehub.dev.db` 內容全部是假資料，**不寫轉換 migration**。
- 新資料庫使用新檔名 `financehub.db`。
- 舊檔案保留不動、不讀取。使用者若想清理，由 README 說明手動刪除。

### 為什麼不寫轉換

寫一個「把明文資料庫轉成加密」的 migration，只會在你自己的電腦上執行一次，之後永遠不會再用到，卻要為它承擔測試與維護成本。既有資料全是假的，重建更乾淨。

**但這個決定必須記入 `04_Decision_Log.md`**，因為未來若有人拿著舊版資料庫升級，需要知道當初是這樣處理的。

- **備份方式**：直接複製 `financehub.db` 到隨身碟或雲端硬碟。檔案本身已加密，只有你的密碼能開。建議說明檔案的實際位置。

## 已知風險

- **階段 0 是整個 Sprint 的成敗關鍵。** 原生模組在打包後載入失敗是最常見的失敗模式，且開發環境測不出來 —— 這是為什麼驗收明確要求實際安裝執行。
- 金鑰導出參數一旦上線就不可變動。參數選擇要在階段 1 開始前確認，不要邊做邊調。
- 99 項測試全部走資料庫，換套件的 API 差異可能造成大量測試調整。若發現需要修改測試的**斷言內容**（不只是建立方式），停下來回報 —— 那可能代表行為真的變了。
- 加密後若資料庫損壞，沒有任何外部工具可以搶救。這使 README 的備份說明成為安全要求，不是選配。
