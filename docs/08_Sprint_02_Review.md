# Sprint 02 Review：手動收支與自訂分類

## 文件資訊

- 日期：2026-07-28
- Sprint：Sprint 02
- 分支：`codex/sprint-02`
- 結果：部分完成；已合併至 `main`

## Sprint Goal 回顧

Sprint 02 已建立手動收入與支出的主要流程、自訂資產／負債類型與收入／支出分類、SQLite 交易一致性，以及月度收入、支出與結餘統計。底層亦保留轉帳、信用卡消費與信用卡繳款能力，但主要畫面依 DEC-021 至 DEC-023 暫時隱藏進階入口。

Sprint Goal 並非全部完成：交易篩選與「將既有交易移至替代分類後刪除」的 UI 流程未實作，已依 G-06 移至 Sprint 03。

## 已完成

- 手動收入與支出的新增、修改及刪除。
- 收入／支出可選擇銀行或現金帳戶，也可不指定帳戶。
- 指定帳戶時同步更新 FinanceHub 帳面餘額。
- 轉帳、信用卡消費與信用卡繳款的底層領域及資料存取能力。
- 月份切換、分月查詢、每批 50 筆載入及月度統計。
- 交易流水依日期分組，顯示當日收支。
- 自訂資產／負債類型與收入／支出分類的新增、重新命名、停用及未使用項目刪除。
- SQLite schema、migration、Repository 與多筆餘額更新的交易一致性。

## 未完成，已移至 Sprint 03

1. 交易篩選：尚未提供依交易類型或分類篩選的介面。
2. 分類重新指派後刪除的 UI 流程：底層 `reassignAndDelete` 已存在，但管理畫面刪除時只呼叫一般 `delete`。因此，使用中的自訂收入或支出分類目前無法在畫面完成移轉與刪除。

## 已知問題，由 Sprint 2.5 處理

1. Electron 端到端驗收未實際完成，當時以 5 秒啟動 smoke test 代替。
2. 現有 E2E selector 已失效。
3. `calculateDailyBalance` 位於 renderer，形成未受測試保護的重複財務計算。
4. renderer 直接比較支出金額與帳戶餘額，決定是否顯示「餘額不足」。
5. renderer 自行依財務項目類型判斷可收付款帳戶。
6. renderer 多處自行取得目前時間，決定月份、日期上限與預設財務時間。
7. 交易餘額影響的 use case 編排位於 SQLite Repository。
8. `allowInactive` 旗標及偽造 `isActive` 狀態被用來反轉舊交易。
9. 使用 `updatedAt` 代替現在時間進行未來交易判斷。
10. 財務月份依本機時區推導，尚未固定為 `Asia/Taipei`。
11. UI 依英文錯誤訊息內容選擇中文文案，其中包含 SQLite 原始錯誤文字。
12. `App.tsx` 與 `TransactionsView.tsx` 遠超結構上限，文案未集中，共用元件位置不符規範。
13. 多數 Application 層測試開啟真實 SQLite，實質上屬於 integration 測試。

1. E2E 啟動加入 `--disable-gpu`，因開發版 Electron 曾出現 GPU subprocess crash。
2. `.gitignore` 排除 `.codex-temp/`，因 Windows 曾鎖住 Electron 暫存目錄。

以上兩項只記錄現況，不在階段 0 修改。

## 階段性相容做法

1. 主畫面隱藏轉帳與信用卡入口，但保留底層能力與既有資料，相容 DEC-021 至 DEC-024。
2. 編輯既有信用卡資料時，臨時插入「信用卡（既有）」選項，避免暫停新功能後無法處理歷史資料。
3. 收入與支出的帳戶為選填，因此「收支流水總額」不必然等於「資產餘額變化」。未來報表必須區分已連結帳戶與未指定帳戶的交易。

## Sprint 結論

Sprint 02 已交付可操作的手動收支底座，但自動化安全網與分層結構不足，且兩項原訂 UI 功能未完成。Sprint 2.5 只處理技術整理及已確認的文案例外；交易篩選與分類重新指派 UI 留在 Sprint 03，不得混入 Sprint 2.5。
