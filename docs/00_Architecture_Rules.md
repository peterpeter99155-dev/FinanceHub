## 1. 分層歸屬

每一層都有正面職責，不只有禁止事項。

### 1.1 `src/domain`

負責：財務概念、不變量、計算與驗證規則。

必須：

- 純函式或純資料結構。
- 能被單元測試直接呼叫，不需要資料庫、Electron、React 或檔案系統。

禁止：

- import 任何 `infrastructure`、`renderer`、`electron`、`node:sqlite`。
- 自行取得系統時間、亂數、UUID 或環境變數。一律由呼叫方傳入。

### 1.2 `src/application`

負責：

- Use case 編排。決定一個使用者動作要依序發生哪些事。
- 驗證外部輸入的型別、範圍與長度。
- 載入所需資料、呼叫 domain 規則、決定要寫入什麼、組裝回傳結果。
- 宣告交易邊界。
- 產生 ID 與時間。

必須：所有「一個動作會影響哪些資料」的決定都在這一層。

禁止：

- import 具體 repository 實作，只能 import `ports` 下的介面。
- 直接撰寫 SQL。

### 1.3 `src/infrastructure`

負責：

- 持久化與外部資源存取。
- 提供交易機制供 application 層使用。
- 把資料庫層級的錯誤（唯一索引衝突、外鍵限制等）轉譯成錯誤代碼。

禁止：

- 呼叫 domain 的驗證或計算函式來決定業務結果。
- 決定「一筆交易要影響哪些帳戶」或「哪些資料要一起被修改」。
- 自行 new 其他 repository。相依一律由外部注入。
- 讓資料庫原始錯誤訊息外流到上層。

允許：資料完整性層級的防護（`CHECK`、`FOREIGN KEY`、唯一索引、交易邊界）。這是第二道防線，不是業務規則的實作位置。

### 1.4 `src/renderer`

負責：顯示與輸入。

禁止：

- 使用 Node.js、檔案系統、`node:sqlite`，或直接使用 `ipcRenderer`。只能透過 preload 暴露的具名 API。
- 實作任何財務計算或財務判斷。

**「財務計算或判斷」的範圍（v1.1 明確化）：**

以下必須由 domain 或 application 產生，renderer 只負責顯示：

- 任何金額的加總、相減、比較。
- 收入／支出／結餘等統計。
- 月份歸屬的判斷。
- 「餘額是否足夠」「是否可刪除」「是否超出上限」等會影響商業判斷的結論。
- 交易類型與可收付款帳戶的分類判斷。

以下屬於一般介面行為，可以留在 renderer：

- 筆數、字數等純計數（例如「3 筆交易」、輸入框剩餘字數）。
- 月份按鈕的顯示與切換狀態。
- 分頁、排序、展開收合等呈現狀態。
- 顏色、圖示、焦點等視覺決定。

判斷標準：**這個數字或結論如果算錯，使用者會不會對自己的財務狀況產生錯誤認知？** 會 → 屬於財務計算，必須上移。

### 1.5 自我檢查的兩個判斷句

放置任何邏輯前，先回答：

1. 這段邏輯如果改用檔案或其他資料庫儲存，需不需要重寫？需要 → 放錯層了。
2. 這段邏輯要寫測試，需不需要開資料庫或啟動 Electron？需要 → 放錯層了。

### 1.6 交易邊界

- 一個 use case 對應一個資料庫交易。
- 交易邊界由 application 層宣告，infrastructure 只提供機制（例如 `runInTransaction` port）。
- 多個帳戶餘額的變動必須在同一個交易內完成，任一步失敗全部回復。

## 2. 錯誤與訊息契約

- 所有 domain 與 application 拋出的錯誤必須帶**穩定的錯誤代碼**，例如 `TX_AMOUNT_OUT_OF_RANGE`、`TX_FUTURE_NOT_ALLOWED`、`ACCOUNT_BALANCE_NEGATIVE`。
- 錯誤代碼集中定義在單一檔案，不得在多處硬編字串。
- 資料庫層級的錯誤必須在 infrastructure 轉成代碼。SQLite 的原始訊息不得傳到上層。
- **跨 IPC 必須明確序列化（v1.1 新增）。** Electron 的 IPC 不會自動保留自訂 Error 的額外屬性，因此不能只定義一個 Error 子類別就視為完成。main 端必須把錯誤轉成明確的結構（例如 `{ ok: false, code, details }`）或以已知方式序列化後再傳出，renderer 端必須能穩定取回代碼。此項需有測試覆蓋。
- **UI 只能依代碼查文案表，禁止比對錯誤訊息內容。** 明確禁止 `error.message.includes(...)`、`indexOf`、正規表達式比對訊息文字。
- 每個代碼必須有對應的中文文案。新增代碼時必須同時補文案，缺文案視為未完成，並以測試檢查代碼與文案一一對應。
- 未知代碼：顯示通用中文訊息，並在開發模式記錄原始錯誤。
- 使用者永遠不應看到英文技術訊息、堆疊追蹤、SQL 或內部識別碼。

## 3. 時間權威

- `now` 只有一個來源：由 application 層注入的時鐘函式。
- domain 不得自行呼叫 `Date.now()` 或 `new Date()` 取得現在時間。
- renderer 不得自行取得現在時間來做財務判斷（例如可輸入的日期上限、預設財務時間、目前月份）。這些一律由 application 提供。
- **禁止用資料自身的欄位（例如 `updatedAt`、`createdAt`）代替 `now` 進行規則判斷。**
- 儲存一律使用 ISO 8601 字串，精度到秒。
- 財務月份歸屬使用固定時區 `Asia/Taipei`，不依機器時區。
- 月份字串由單一函式產生，不得在多處各自計算。
- 測試必須能注入固定時鐘。

## 4. 金額與識別碼

- 金額一律以整數表示（TWD 元），禁止任何浮點數運算。
- 所有加減必須經過安全整數範圍檢查。
- 上限集中定義為常數，不得在多處硬編數字。
- 金額的顯示格式集中在單一模組。
- ID 由 application 層產生，且必須可注入，讓測試能決定 ID。

## 5. 資料庫與 migration 紀律

- **已套用過的 migration 不得修改，只能新增。**

  「不得修改」的明確範圍（v1.2 補充）：SQL 字串內容、版本號、順序與位置，一律不得變動。
  說明文字與歷史註解**不得寫在 migration 定義區塊內部**，應放在該資料結構之外（例如檔案頂部的說明區塊），主要記錄仍以 `04_Decision_Log.md` 為準。此界線的目的是讓「動到 migration」永遠是一個明確、可一眼看出的行為，不留「只是加註解」的模糊空間。
- 新的 migration 一個做一件事。schema 變更與預設資料寫入不混在同一個版本。
- 不得用內容重複的 migration 掩蓋前一版的錯誤。若前一版有誤，新增修正 migration，並在 `04_Decision_Log.md` 記錄原因。
- 預設資料寫入必須可重複執行而不產生重複列（使用 `INSERT OR IGNORE` 或等效做法）。
- 每個新 table 必須說明它的索引對應哪一個實際查詢。
- 破壞性變更（改欄位、刪欄位、改語意）必須附「升級前後淨資產一致」的測試。

### 5.1 歷史例外

本規範建立前已套用的 migration，若不符合上述規則，一律**保留原狀並記錄為歷史例外**，不得回頭修改或拆解。已知例外：

- Migration 4 同時包含 schema 變更與預設分類寫入，不符合「一個 migration 一件事」。此為規範建立前的既成事實，保留不動。
- Migration 5 與 Migration 4 的預設分類 `INSERT` 內容相同，屬資料修復 migration（舊版介面曾允許刪除預設分類），保留不動。

## 6. 介面層結構

- 單一 `.tsx` 檔案上限 **300 行**，超過必須拆分。此為機械門檻，不接受個案協商。
- 單一元件 `useState` 上限 **8 個**，超過改用單一狀態物件或抽出自訂 hook。
- 表單、列表、單列、金額顯示、月份切換各自為獨立元件。
- 共用元件放 `src/renderer/components`，不得留在 `src/renderer` 根目錄。
- 資料取得與狀態管理集中於容器元件或自訂 hook。呈現元件不呼叫 API。
- 所有使用者可見文案集中於 labels / messages 模組，不散落在元件內。

### 6.1 不得用 `setTimeout` 協調 UI 狀態或焦點

**禁止**用 `setTimeout`（或任何脫離渲染週期的延遲 callback）處理焦點、捲動、狀態同步等需要與畫面更新對齊的行為。

一律使用 React 的生命週期（`useLayoutEffect` 等），並綁定明確的觸發條件。

#### 事故來源

一個從 Sprint 01 就存在、直到 Sprint 2.5 建立端到端測試才被發現的靜默資料錯誤。

錯誤寫法：

```ts
function startEditing(item) {
  setDraft({ ...item });
  window.setTimeout(() => {
    nameInputRef.current?.focus();
  }, 0);
}
```

實際發生的競速：

```text
點擊編輯 → setDraft 載入既有資料 → 安排延遲聚焦
        → 使用者開始輸入新金額
        → 延遲 callback 此時才執行，焦點被搶回名稱欄位
        → 後續數字輸入到名稱欄位
        → 儲存時送出舊金額
```

實際後果：房貸名稱變成「示範房貸4900000」，金額仍是舊的 `5,000,000`，資料庫存的也是舊值，淨資產因此長期錯誤。**使用者完全不會收到任何錯誤訊息。**

正確寫法：

```tsx
useLayoutEffect(() => {
  if (editingId) {
    formPanelRef.current?.scrollIntoView({ behavior: 'smooth', block: 'start' });
  }
  nameInputRef.current?.focus();
}, [editingId, formPanelRef, nameInputRef]);
```

關鍵差別：`useLayoutEffect` 在瀏覽器繪製**之前**同步執行，使用者不可能在那之間輸入，因為畫面還沒顯示。`setTimeout` 則脫離渲染週期，執行時機不可控。

#### 不在此限的正當用途

`setTimeout` 本身不是禁忌，**刻意的延遲行為**可以使用：

- 輸入防抖（例如自動儲存延遲 600ms）
- 通知訊息在數秒後自動消失

判斷標準：**這個延遲是「功能的一部分」，還是「為了等畫面更新」？** 後者一律禁止。

## 9. 測試規範

- 每條商業規則至少一個 domain 層測試。
- 每個 use case 至少一個 application 層測試，**使用假 repository，不開啟資料庫**。開資料庫的測試屬於 integration 測試，可以有，但不能取代 application 測試。
- 涉及多筆資料同時變動的寫入，必須有 rollback 測試（此項屬 infrastructure 測試，需開資料庫）。
- **禁止為了讓測試通過而放寬 domain 規則。** 規則需要改，必須先改文件並取得確認。
- 禁止為了繞過驗證而在測試或程式中偽造資料狀態（例如強制把停用改成啟用）。
- 測試必須真的會執行且真的會失敗。新增或修復測試時，應確認故意改壞受測邏輯時測試會紅。
- 交付時必須附上測試的實際執行輸出，不接受「應該可以通過」。

### 9.1 Migration 測試要求（v1.1 修正）

原版本要求「每個 migration 都要有重複執行安全測試」。此要求字面上不可執行：含 `CREATE TABLE` 的 SQL 重跑必然失敗，migration 的冪等性是由 `schema_migrations` 保證只執行一次，而非每段 SQL 可重跑。修正為以下三條：

1. **系統層冪等性**：同一個資料庫連續開啟兩次，不會重複套用任何 migration，也不會產生重複的預設資料。
2. **Seed 冪等性**：所有預設資料寫入必須可安全重複執行。
3. **資料一致性**：只有會改變既有財務資料或 schema 語意的 migration，才要求「升級前後總資產、總負債與淨資產一致」的測試。純新增 table 或 index 的 migration 不需要。

### 9.2 修 bug 必須新增「該 bug 重現就會失敗」的測試

修復任何 bug 時，除了驗證正確結果出現，**必須另外斷言該 bug 的具體錯誤症狀不存在**。

只驗證「正確結果」不足以防止回歸，因為換一種方式壞掉時，正確結果也可能碰巧成立。

範例（來自 6.1 節那次事故）：

```ts
// 驗證正確結果
await expect(page.getByTestId('item-name')).toHaveValue('示範房貸');
await expect(page.getByTestId('liability-group')).toContainText('TWD 4,900,000');

// 同時明確斷言錯誤症狀不存在
await expect(
  page.getByText('示範房貸4900000', { exact: true }),
).toHaveCount(0);
```

同時應驗證造成該 bug 的中間狀態，例如上例額外驗證了「輸入金額後焦點仍留在金額欄位」。

### 9.2.1 驗收前必須先確認環境能力

紅燈只有在「環境本來就有能力執行這項測試」的前提下才可解讀。

執行下列測試前，必須先確認對應的環境能力，並在回報中說明確認結果：

| 測試類型 | 必須先確認 |
|---|---|
| Electron 啟動類測試 | 有 GUI 能力；`node_modules/electron/dist/electron.exe` 與 `path.txt` 確實存在 |
| 需下載資源的打包與安裝 | 網路可連線至所需來源 |
| 原生模組相關測試 | `.node` binary 確實存在且架構正確 |

**若環境能力不足，回報「無法執行」而不是「測試失敗」。** 兩者的處理方式完全不同：前者要修環境，後者要修程式。

#### 為什麼需要這一條

本專案曾三次因環境限制產生假紅燈，每次都花掉一輪來分辨是產品問題還是環境問題：

1. 沙箱沒有 GUI，Electron 測試無法啟動。
2. 沙箱阻擋網路，打包資源下載失敗。
3. 沙箱阻擋網路導致 `electron` 套件的 postinstall 未下載執行檔，測試回報「找不到路徑」，看起來像 Electron 版本不相容。

第 3 次尤其危險：它差點導致放棄一條可行的技術路線，理由卻只是安裝沒完成。

**假紅燈與假綠燈同樣有害。** 假綠燈讓你誤以為驗過了，假紅燈讓你誤判產品有問題並做出錯誤的技術決策。

### 9.3 不得用延長等待或 sleep 掩蓋競速

當測試間歇性失敗時，**禁止**用下列方式處理：

- 加入 `sleep` 或固定延遲
- 延長 timeout
- 在操作前多點一次欄位
- 只等待某個無關元素出現

這些做法只會**降低重現機率**，不會保護真實使用者 —— 使用者的操作速度不受你的測試等待控制。

正確處理順序：

1. 先確認是**穩定失敗**還是**間歇失敗**：同一個建置版本連續執行至少 10 次並記錄結果。
2. 間歇失敗代表存在真實競速，必須找出根因並修掉產品程式，不是修測試。
3. 若確認是測試本身缺少對「狀態已就緒」的等待（例如等待表單載入既有值），可以補上該等待 —— 但那是斷言狀態，不是延遲時間。
4. **不穩定的測試不得留在專案裡。** 留著會訓練所有人忽略紅燈，而「紅燈一定代表有問題」是整個安全網唯一的價值來源。

#### 附帶影響

間歇失敗會讓 `git bisect` 這類二分法工具失效，因為它假設同一版本每次結果相同。因此第 1 步不能跳過。

## 10. Git 與 diff 紀律

- 一個 commit 一件事。
- 禁止把換行、縮排、自動格式化等無關變更混入功能 commit。
- 專案以 LF 為儲存格式，並以 `.gitattributes` 明文宣告，避免不同機器或不同 `core.autocrlf` 設定造成差異。
- 若確實需要一次性全域格式正規化，必須**先確認問題真實存在**（在乾淨工作區上重現），再單獨一個 commit 執行，訊息標明「僅格式，無行為變更」，且不得混入任何邏輯修改。
- **不得因為文件或他人描述提到格式問題，就主動執行全庫改寫。** 先驗證再行動。
- 交付前必須自己檢視 diff 的檔案清單。檔案數或行數異常擴大時，必須主動說明原因。

## 13. 規範必須盡可能機械化（元規則）

新增或修改本文件的任何條文時，必須先回答：**這一條能不能用測試強制？**

- **能** → 必須同時建立測試，並在條文中註明由哪個測試強制。
- **不能** → 才以文字條文形式存在。

理由：寫在文件裡的規則靠人與 AI 自律，會隨時間腐爛；寫成測試的規則不會。

### 目前已機械化的規範

| 規範 | 強制方式 | 位置 |
