## 文件資訊

- 日期：2026-07-28
- 狀態：待確認

## 本文件的定位

產品文件定義「要做什麼」與「財務規則是什麼」。
本文件定義「程式可以長什麼樣」。

兩者不重疊：

- `01_Product_Vision.md`、`02_Requirements.md`、`03_Business_Rules.md` 描述使用者與財務行為。
- 本文件描述結構、歸屬、契約與紀律。

## 優先順序

## 1. 分層歸屬

每一層都有正面職責，不只有禁止事項。

### 1.1 `src/domain`

負責：

- 財務概念、不變量、計算與驗證規則。

必須：

- 純函式或純資料結構。
- 能被單元測試直接呼叫，不需要資料庫、Electron、React 或檔案系統。

禁止：

- import 任何 `infrastructure`、`renderer`、`electron`、`node:sqlite`。
- 自行取得系統時間、亂數、UUID 或環境變數。這些一律由呼叫方傳入。

### 1.2 `src/application`

負責：

- Use case 編排。決定一個使用者動作要依序發生哪些事。
- 驗證外部輸入的型別、範圍與長度。
- 載入所需資料、呼叫 domain 規則、決定要寫入什麼、組裝回傳結果。
- 宣告交易邊界。

必須：

- 所有「一個動作會影響哪些資料」的決定都在這一層。

禁止：

- import 具體 repository 實作，只能 import `ports` 下的介面。
- 直接撰寫 SQL。

### 1.3 `src/infrastructure`

負責：

- 持久化與外部資源存取。把 domain 資料存進 SQLite、讀回來、維護 schema。
- 提供交易機制供 application 層使用。

禁止：

- 呼叫 domain 的驗證或計算函式來決定業務結果。
- 決定「一筆交易要影響哪些帳戶」或「哪些資料要一起被修改」。
- 自行 new 其他 repository。相依一律由外部注入。

允許：

- 資料完整性層級的防護：`CHECK`、`FOREIGN KEY`、唯一索引、交易邊界。這是第二道防線，不是業務規則的實作位置。

### 1.4 `src/renderer`

負責：

- 顯示與輸入。

禁止：

- 使用 Node.js、檔案系統、`node:sqlite`，或直接使用 `ipcRenderer`。只能透過 preload 暴露的具名 API。
- 實作任何財務計算。畫面顯示的每個數字都必須由 domain 或 application 算出。

### 1.5 自我檢查的兩個判斷句

放置任何邏輯前，先回答：

1. 這段邏輯如果改用檔案或其他資料庫儲存，需不需要重寫？
   需要 → 放錯層了。
2. 這段邏輯要寫測試，需不需要開資料庫或啟動 Electron？
   需要 → 放錯層了。

### 1.6 交易邊界

- 一個 use case 對應一個資料庫交易。
- 交易邊界由 application 層宣告，infrastructure 只提供機制（例如 `runInTransaction` port）。
- 多個帳戶餘額的變動必須在同一個交易內完成，任一步失敗全部回復。

## 2. 錯誤與訊息契約

- 所有 domain 與 application 拋出的錯誤必須帶**穩定的錯誤代碼**，例如 `TX_AMOUNT_OUT_OF_RANGE`、`TX_FUTURE_NOT_ALLOWED`、`ACCOUNT_BALANCE_NEGATIVE`。
- 錯誤代碼集中定義在單一檔案，不得在多處硬編字串。
- 跨 IPC 傳遞時必須保留代碼，不得只傳 `Error.message`。
- **UI 只能依代碼查文案表，禁止比對錯誤訊息內容。**
  明確禁止 `error.message.includes(...)`、`indexOf`、正規表達式比對訊息文字。
- 每個代碼必須有對應的中文文案。新增代碼時必須同時補文案，缺文案視為未完成。
- 未知代碼：顯示通用中文訊息，並在開發模式記錄原始錯誤。
- 使用者永遠不應看到英文技術訊息、堆疊追蹤、SQL 或內部識別碼。

## 3. 時間權威

- `now` 只有一個來源：由 application 層注入的時鐘函式。
- domain 不得自行呼叫 `Date.now()` 或 `new Date()` 取得現在時間。
- **禁止用資料自身的欄位（例如 `updatedAt`、`createdAt`）代替 `now` 進行規則判斷。**
- 儲存一律使用 ISO 8601 字串，精度到秒。
- 財務月份歸屬使用固定時區 `Asia/Taipei`，不依機器時區。
- 月份字串由單一函式產生，不得在多處各自計算。
- 測試必須能注入固定時鐘。

---

## 4. 金額與識別碼

- 金額一律以整數表示（TWD 元），禁止任何浮點數運算。
- 所有加減必須經過安全整數範圍檢查。
- 上限集中定義為常數，不得在多處硬編數字。
- 金額的顯示格式集中在單一模組。
- ID 由 application 層產生，且必須可注入，讓測試能決定 ID。

---

## 5. 資料庫與 migration 紀律

- **已套用過的 migration 不得修改，只能新增。** 包含 SQL 內容、版本號與順序。
- 一個 migration 一件事。schema 變更與預設資料寫入不混在同一個版本。
- 不得用內容重複的 migration 掩蓋前一版的錯誤。若前一版有誤，新增修正 migration，並在 `04_Decision_Log.md` 記錄原因。
- 每個新 table 必須說明它的索引對應哪一個實際查詢。
- 破壞性變更（改欄位、刪欄位、改語意）必須附「升級前後淨資產一致」的測試。
- 預設資料寫入必須可重複執行而不產生重複列。

---

## 6. 介面層結構

- 單一 `.tsx` 檔案上限 **300 行**，超過必須拆分。
- 單一元件 `useState` 上限 **8 個**，超過改用單一狀態物件或抽出自訂 hook。
- 表單、列表、單列、金額顯示、月份切換各自為獨立元件。
- 共用元件放 `src/renderer/components`。
- 資料取得與狀態管理集中於容器元件或自訂 hook。呈現元件不呼叫 API。
- 所有使用者可見文案集中於 labels / messages 模組，不散落在元件內。

---

## 7. 命名

- 以 `00_Glossary.md` 為唯一依據。
- 同一概念在文件、程式、UI 三處的名稱必須能互相對應。
- 若程式需要兩個不同型別表示相近概念，必須在術語表登記兩者的差異與轉換位置。
- 不得在程式中引入術語表沒有的新概念名稱；需要新概念時先更新術語表。

---

## 8. 相依與範圍

- 新增第三方套件前必須說明：為什麼現有能力做不到、影響哪些層、是否會進入 renderer、授權是否可商用。
- 不得為單一功能引入框架級套件。
- 不得為了方便而擴大 Electron 或 Node.js 對畫面層的曝光。

---

## 9. 測試規範

- 每條商業規則至少一個 domain 層測試。
- 每個 use case 至少一個 application 層測試，使用假 repository，不開資料庫。
- 涉及多筆資料同時變動的寫入，必須有 rollback 測試。
- 每個 migration 必須有「重複執行安全」與「升級後淨資產不變」的測試。
- **禁止為了讓測試通過而放寬 domain 規則。** 規則需要改，必須先改文件並取得確認。
- 禁止為了繞過驗證而在測試或程式中偽造資料狀態（例如強制把停用改成啟用）。

---

## 10. Git 與 diff 紀律

- 一個 commit 一件事。
- 禁止把換行、縮排、自動格式化等無關變更混入功能 commit。
- 換行統一 LF，由 `.gitattributes` 強制。
- 若必須做全域格式化，單獨一個 commit，訊息標明「僅格式，無行為變更」。
- 交付前必須自己檢視 diff 的檔案清單。檔案數或行數異常擴大時，必須主動說明原因。

---

## 11. 結構性完成定義

除各 Sprint 自訂的 DoD 外，以下每次都適用：

- 新增邏輯位於正確的層，並能用第 1.5 節的兩個判斷句自我說明。
- 沒有為了繞過設計而新增的旗標、參數或偽造狀態。
- 沒有依賴錯誤訊息文字的流程控制。
- 沒有超過行數或狀態數上限的檔案。
- 沒有修改已套用的 migration。
- diff 不含與本次任務無關的格式變更。
- 文件與程式的列舉、型別、預設值一致。

任何一項不符，必須在回報中明確列出，不得默默交付。

---

## 12. 衝突與例外

- 需要例外時：停止實作，說明理由與影響，取得同意後記入 `04_Decision_Log.md`。
- 不得自行判斷「這次比較特殊」而略過本文件。
- 發現本文件本身有問題時，提出修改建議，不要直接違反。
