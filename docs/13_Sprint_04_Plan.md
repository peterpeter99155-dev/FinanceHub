## Sprint Goal

讓使用者開始使用真實財務資料後，能在應用程式內看懂資料保存狀態，
並以可驗證、可保留多個版本的方式建立本機加密備份。

本 Sprint 的核心交付是：

1. 針對現有介面進行必要的文案與排版調整。
2. 提供常駐的資料與備份資訊。
3. 完成可靠的手動「立即備份」。
4. 解鎖後依間隔檢查並執行最小可用的自動備份。
5. 保留最近 7 份成功備份。

## 已確認的產品決策

### 1. 備份位置

- 預設使用 FinanceHub 資料目錄下的 `backups` 子目錄。
- Sprint 04 不提供使用者自選備份資料夾。
- 畫面必須顯示實際備份位置。
- 不加入雲端服務、同步或外部網路權限。

### 2. 自動備份預設

- 預設開啟。
- 每次成功解鎖後檢查備份間隔。
- 距離上次成功備份滿 24 小時才執行自動備份。
- 同一次應用程式啟動最多自動嘗試一次。
- 自動備份失敗不得阻止使用者進入主畫面，但必須明確提示失敗。

### 3. 保留策略

- 預設保留最近 **7 份成功備份**。
- Sprint 04 的產品介面可提供 `3`、`7`、`14`、`30` 四個保留份數，
  預設選擇 `7`。
- 不實作每日／每週／每月分層保留。
- 只有新備份完整建立並驗證成功後，才能清理超額的舊備份。
- 清理失敗不得把新備份改判為失敗，但必須顯示清理警告。

### 4. 上次備份時間

- 「上次備份時間」只代表最後一次**成功完成且通過驗證**的備份。
- 失敗時間與錯誤狀態必須另外顯示，不得覆蓋最後成功時間。
- 不得以資料庫修改時間、資料夾時間或應用程式關閉時間代替。

### 5. 備份格式

- 每份備份使用一個獨立目錄。
- 每份至少包含：
  - 加密資料庫快照
  - 對應的 metadata sidecar
  - 不含敏感財務內容的 manifest
- Sprint 04 不製作 ZIP。
- 備份不得包含主密碼、導出金鑰、測試密碼、敏感憑證或未加密財務
  內容。
- manifest 的欄位、版本、雜湊與時間格式須由 CODEX 在 S4-00 提案，
  經確認後寫入正式規格。

### 6. 一致性快照與寫入閘門

- 正式採用方案 A：

  ```text
  全域寫入閘門
  → 等待既有寫入完成
  → WAL checkpoint(TRUNCATE)
  → 確認 busy = 0
  → 複製資料庫與 metadata sidecar
  → 計算 SHA-256
  → 最後寫入 manifest
  → 原子發布備份目錄
  → 解除寫入閘門
  ```

- 不使用 `better-sqlite3-multiple-ciphers` 的 `database.backup()`；S4-00
  已實測加密來源與 API 自行建立的目標資料庫格式不相容。
- 寫入閘門設於 main／application 邊界，是唯一安全邊界；不得只靠
  renderer 停用按鈕。
- 已開始的資料庫寫入先完成；新寫入依抵達順序進入 FIFO，最多
  `100` 筆。
- 備份期間允許讀取。所有資料庫寫入，包括財務資料、類型、分類與
  備份設定，都必須經過同一閘門。
- checkpoint busy timeout 固定為 `500 ms`；回報 `busy !== 0` 時，
  該次備份失敗、不得複製資料庫，並須解除閘門、依序繼續排隊寫入。
- 備份成功或失敗都不得使已排隊的寫入遺失或無限等待。
- 同一時間只允許一個備份工作；第二個備份要求不得進入寫入佇列。
- 應用程式關閉時須完成已接受的財務寫入。未原子發布的備份一律
  不算成功；未完成目錄由下次啟動安全清理。
- 正常關閉也會等待關閉要求前已接受的備份工作完成：若它在關閉前
  完成驗證與原子發布，仍是成功備份；若程式遭強制終止且尚未發布，
  則不算成功，留下的 `.creating-*` 由下次啟動安全清理。正常關閉
  不得在備份工作仍持有資料庫或檔案 handle 時直接關閉 connection。

### 7. Manifest v1 與備份狀態

- 正式備份目錄以 `backupId` 保證唯一，不得只依時間命名。
- `createdAt` 是開始建立快照的時間。
- `completedAt` 是全部檔案完成格式、大小與雜湊驗證，準備原子發布
  的時間。
- `completedAt` 只用於通過格式與雜湊驗證後的備份排序；它不是
  密碼學可信時間，也不能用於對抗系統時鐘回撥。
- manifest 保留資料庫 schema 版本，但值必須從資料庫實際讀取
  「已套用的最高 migration 版本」，不得由應用程式版本或常數硬編碼。
- manifest 不得包含使用者名稱、完整來源路徑、帳戶名稱、金額、
  交易數、salt、key verifier、密碼或金鑰。
- 備份設定與最近錯誤狀態存入加密資料庫。
- 最後成功備份時間與現存有效份數必須由備份目錄中的 manifest、
  資料庫及 sidecar 通過格式與 SHA-256 驗證後重建；資料庫紀錄只能
  作為快取，不得是唯一真相。

Manifest v1 欄位固定為：

```json
{
  "formatVersion": 1,
  "backupId": "UUID",
  "createdAt": "ISO 8601 UTC",
  "completedAt": "ISO 8601 UTC",
  "applicationVersion": "x.y.z",
  "databaseSchemaVersion": 5,
  "database": {
    "file": "financehub.db",
    "sizeBytes": 0,
    "sha256": "lowercase hex"
  },
  "metadata": {
    "file": "financehub.db.metadata.json",
    "sizeBytes": 0,
    "sha256": "lowercase hex"
  },
  "encryption": {
    "formatVersion": 1,
    "kdfVersion": 1
  }
}
```

上例的 `databaseSchemaVersion: 5` 只表示目前資料庫的實際最高
migration；實作不得把 `5` 寫成固定值。

### 8. 自動備份與介面範圍

- 首次尚無任何有效備份時，在成功設定或解鎖後立即嘗試第一份自動
  備份。
- 手動備份成功會重設 24 小時間隔；手動或自動備份失敗都不重設。
- 關閉自動備份只停止自動嘗試，不影響手動備份、不隱藏既有狀態，
  也不刪除任何備份。
- 重新開啟自動備份時立即檢查間隔；若已到期則在該次啟動嘗試一次。
- 備份介面置於獨立全域設定入口，不放入資產、負債或收支表單。
- 介面可提供「開啟資料夾」，但 renderer 只能呼叫窄 IPC，不得直接
  使用 Node.js 或檔案系統。
- 正式介面必須移除「僅限假資料」，或改成只在開發／測試環境顯示
  的正確環境標示。
- 依 G-04，手動輸入介面只允許選擇 `confirmed` 與
  `pending_confirmation`；`automatic`、`estimated`、`stale` 不得
  出現在使用者選單。
- 其他 S4-00 介面候選不納入 Sprint 04，不得擴張成全面改版。
- Sprint 04 不做還原 UI，但必須更新 README 手動還原程序，並完成
  自動化隔離復原測試與安裝端復原演練。
- 驗證分成三層，不得互相取代：
  - 執行時機械驗證：格式、必要檔案、大小、雜湊、受控路徑與原子
    發布。
  - 自動化完整復原驗證：以固定假密碼在隔離目錄開啟備份，驗證
    最新財務資料、交易、統計與淨資產。
  - 安裝端復原演練：使用實際安裝版與隔離 user-data，依 README
    完整走過手動還原。

# 階段 1　備份格式與一致性核心

## S4-10　定義備份格式 v1

正式規格至少必須固定：

- 備份格式版本固定為 `1`。
- 正式目錄以 `backupId` 命名並保證唯一；時間不得作為唯一鍵。
- 資料庫快照檔名固定為 `financehub.db`。
- metadata sidecar 檔名固定為 `financehub.db.metadata.json`。
- manifest 檔名固定為 `manifest.json`，使用 UTF-8 JSON。
- manifest 欄位依「已確認的產品決策」第 7 節，不得任意增刪 v1
  必要欄位。讀取器可忽略不影響 v1 語意的未知欄位；未知
  `formatVersion` 必須拒絕。
- 資料庫與 sidecar 分別使用 SHA-256；先驗證 manifest 格式與檔名，
  再驗證大小，最後重算雜湊。
- schema 版本必須從實際 migration 狀態讀取最高版本，不得硬編碼。
- 暫存目錄使用 `.creating-<backupId>`；只有完整驗證並原子重新命名
  後才是成功備份。
- 較新格式、未知格式及損壞備份的錯誤語意。

格式一旦有正式備份產物，就不得偷偷修改既有版本定義；任何不相容
變更都必須建立新版本。

## S4-11　一致性快照

- 必須透過獨立 infrastructure 介面建立備份。
- 財務 domain 與 application 不得依賴 Electron、檔案系統或 SQLite。
- renderer 不得直接操作檔案系統。
- main／application 必須提供全域 FIFO 寫入閘門，佇列上限 `100`。
- 已開始的寫入先完成；新寫入排隊。成功、失敗與 checkpoint busy
  都必須解除閘門並依序繼續佇列。
- 備份期間允許讀取，但所有資料庫寫入都必須經過同一閘門。
- checkpoint 使用 `wal_checkpoint(TRUNCATE)` 與 `500 ms` busy
  timeout；`busy !== 0` 時不得進入複製。
- 不使用 `database.backup()`，也不得只複製仍含未 checkpoint 最新
  資料的主資料庫檔案。
- 開始前確認來源資料庫與 metadata 存在且狀態有效。
- checkpoint 成功後複製資料庫與 sidecar，計算雜湊，最後才寫入
  manifest。
- 快照完成後驗證資料庫、metadata 與 manifest；不得為驗證而保存、
  回傳或重新要求主密碼。
- 任一步驟失敗時，不得把暫存內容視為成功備份。

## S4-12　原子完成與故障復原

- 先在受控暫存目錄建立完整備份。
- 所有檔案完成寫入、同步與驗證後，才原子移入正式備份名稱。
- 同名衝突不得覆蓋既有成功備份。
- 程式中止、磁碟空間不足、權限錯誤、雜湊不符與 metadata 遺失都
  必須有穩定錯誤代碼。
- 下次啟動可辨識並安全處理未完成項目，不得誤刪成功備份或使用者
  其他檔案。
- 應用程式關閉時先停止接受新 IPC 寫入，完成已接受的財務寫入，
  並等待關閉要求前已接受的備份工作。已完成原子發布者可記為成功；
  強制中止時未發布者不得補記為成功。
- 清理只能處理備份根目錄的直接子目錄，拒絕 symlink、junction 與
  其他 reparse point。
- 不得跟隨連結，不得對未知內容使用遞迴刪除。刪除前先將已驗證目標
  原子移入同一根目錄內的 quarantine，再逐一刪除預期的一般檔案與
  空目錄。

# 階段 2　手動備份與狀態

## S4-20　手動「立即備份」

- 提供窄 IPC 供 renderer 要求備份。
- main 驗證狀態並執行備份。
- 同一時間只允許一個備份工作。
- 重複點擊不得建立競速或多份不完整備份。
- UI 必須顯示進行中、成功、失敗及清理警告。
- 自動結果必須允許使用者再次手動重試。

## S4-21　備份狀態

至少提供：

- 備份是否啟用。
- 備份位置。
- 最後成功備份時間。
- 最近失敗時間與錯誤訊息。
- 目前保留份數設定。
- 從備份目錄重建的現存有效備份份數。
- 備份是否正在進行。

時間由 main／application 邊界提供，renderer 不得自行判斷是否已達
自動備份間隔。設定與最近錯誤可存入加密資料庫；最後成功時間與有效
份數必須從通過格式、大小及雜湊驗證的備份目錄重建。

# 階段 3　自動備份與保留策略

## S4-30　解鎖後間隔檢查

- 成功解鎖後檢查最後成功備份時間。
- 首次沒有有效備份時立即嘗試。
- 滿 24 小時才嘗試自動備份。
- 同一次啟動最多嘗試一次。
- 自動備份不得使用固定 `setTimeout` 排程或協調狀態。
- 自動備份失敗不阻擋主畫面，但必須留下可見狀態與重試入口。
- 手動備份成功重設 24 小時間隔；任何失敗都不重設。
- 關閉自動備份只停止自動嘗試，不影響手動備份、既有狀態或備份
  檔案。
- 重新開啟自動備份時立即檢查間隔。

## S4-31　最近 N 份保留

- 可選 `3`、`7`、`14`、`30`，預設 `7`。
- 只計入 FinanceHub 建立且通過格式驗證的成功備份。
- 只在 manifest 格式及 DB／sidecar 雜湊都通過後，按
  `completedAt` 排序；`completedAt` 不稱為可信時間，也不承諾抵抗
  系統時鐘回撥。
- 只有新備份成功後才執行清理。
- 刪除前再次確認目標位於指定 `backups` 目錄內，且符合 FinanceHub
  備份格式。
- 拒絕 symlink、junction、其他 reparse point、巢狀目錄與未知內容。
- 刪除前先 quarantine，再逐一刪除三個預期的一般檔案；不得使用會
  跟隨未知目錄結構的遞迴刪除。
- 清理失敗須回報警告並保留新備份。

# 階段 4　介面調整

## S4-40　資料與備份介面

依 S4-01 確認的資訊架構提供常駐入口，至少可查看：

- 資料位置。
- 備份位置。
- 最後成功備份時間。
- 最近失敗狀態。
- 自動備份開關。
- 24 小時間隔說明。
- 保留份數。
- 「立即備份」。
- 「開啟資料夾」。

畫面必須使用一般使用者可理解的文字；檔名與路徑等技術資訊可顯示，
但不得讓使用者必須理解 WAL、sidecar 或 IPC 才能正確操作。
入口必須位於獨立的全域設定區；renderer 的「開啟資料夾」只能呼叫
窄 IPC，不得直接接觸檔案系統。

## S4-41　介面文案與排版

- 只實作 S4-01 經使用者確認的清單。
- 移除正式介面的「僅限假資料」，或限制為只在開發／測試環境顯示
  的正確環境標示。
- 手動資料狀態選單只顯示 `confirmed` 與
  `pending_confirmation`；`automatic`、`estimated`、`stale` 仍保留
  在資料模型，但不得供使用者手動選擇。
- 不擴張為全面 UI redesign。
- 桌面主要視窗與窄視窗皆不得產生非預期水平捲動。
- 維持鍵盤操作、可見焦點與可辨識的無障礙名稱。
- 不得以 `setTimeout` 協調焦點、捲動或狀態。

## S4-42　README 手動還原程序

README 必須以一般使用者可執行的步驟說明：

1. 完全關閉 FinanceHub。
2. 選擇一份 manifest、資料庫與 sidecar 都通過驗證的完整備份。
3. 先將目前的 `financehub.db`、`financehub.db.metadata.json`，以及
   若存在的 `financehub.db-wal`、`financehub.db-shm`、
   `financehub.db-journal` 一起移到另一個安全目錄；不得直接覆蓋、
   混用新舊檔案或只保留資料庫／sidecar 其中一個。
4. 將備份內的 `financehub.db` 與
   `financehub.db.metadata.json` 一起複製到 FinanceHub 資料目錄。
5. 重新開啟 FinanceHub，使用建立該備份時的原主密碼解鎖。
6. 確認最新財務項目、交易與淨資產正確後，才可視為還原成功。

README 必須警告：缺少資料庫或 sidecar、使用錯誤 sidecar、忘記原
主密碼，皆無法還原。`manifest.json` 用於選擇與驗證完整備份，不得
把未通過 manifest 與雜湊驗證的目錄當作可還原來源。

# 階段 5　驗收與回報

## S4-50　自動化測試

至少涵蓋：

- 一致性快照包含最新已提交資料。
- WAL 有未 checkpoint 資料時仍可正確備份。
- 資料庫與 metadata 成對保存。
- manifest 與所有雜湊可驗證。
- 寫到一半中止不會產生成功備份。
- 磁碟空間不足、權限錯誤及同名衝突。
- 連續點擊只建立一個備份工作。
- 上次成功時間只在完整成功後更新。
- 失敗不覆蓋最後成功時間。
- 未滿 24 小時不自動備份。
- 滿 24 小時在解鎖後自動嘗試一次。
- 自動失敗不阻止使用主畫面。
- 第 8 份成功後只保留最近 7 份。
- 清理只觸及受控備份目錄與已驗證項目。
- symlink、junction、reparse point 與未知內容一律拒絕且不被跟隨。
- 清理失敗保留新備份並顯示警告。
- FIFO 寫入依序繼續，佇列超過 100 筆時穩定失敗。
- checkpoint `busy !== 0` 時不複製、不重設間隔並正常釋放佇列。
- 關閉期間完成已接受的財務寫入，未發布目錄不算成功且下次可清理。
- 手動成功重設 24 小時間隔；失敗不重設。
- 關閉自動備份不影響手動備份與既有檔案，重新開啟立即檢查間隔。
- 最後成功時間與有效份數可在清空資料庫快取後由備份目錄重建。
- 正式版不顯示不正確的「僅限假資料」。
- 手動資料狀態選單不含三個系統專用狀態。
- production bundle 不含密碼、金鑰或真實財務資料。
- 自動化完整復原：在隔離目錄以固定假密碼開啟備份，驗證最新財務
  項目、交易、統計及淨資產。

## S4-51　完整驗收

開工版計畫必須依 S4-00 回報補足確切指令與數量。最低要求：

- `npm.cmd run typecheck`
- `npm.cmd run lint`
- `npm.cmd run verify`
- `npm.cmd test`
- `npm.cmd run test:e2e`
- `npm.cmd run test:electron` 連續 10 次
- `npm.cmd run test:package-smoke`
- `npm.cmd run make`
- 最新安裝檔乾淨安裝與實際備份操作驗收
- README 手動還原程序一致性檢查

安裝端至少驗證：

1. 解鎖後可看到資料與備份狀態。
2. 立即備份成功建立完整的三件式備份。
3. 備份內容不含已知明文財務字串。
4. 關閉並重開後仍能看到正確的最後成功時間。
5. 模擬超過間隔後，解鎖觸發一次自動備份。
6. 建立第 8 份成功備份後只保留最近 7 份。
7. 自動備份失敗時仍可進入主畫面並手動重試。
8. 關閉應用程式後，依 README 將完整備份放入隔離 user-data 目錄，
   用原測試密碼解鎖並確認最新財務項目、交易與淨資產。
9. 還原演練缺少資料庫、sidecar 或 manifest 任一項時必須拒絕。

## S4-52　Sprint Review

Review 至少回報：

- 完成內容。
- 修改檔案。
- 驗證與測試結果。
- 尚未完成項目。
- 已知風險與待確認事項。
- 備份格式 v1 與一致性方案。
- 故障注入結果。
- 是否新增外部套件、權限或網路能力。
- 是否修改既有 migration、測試斷言或 IPC。
- 下一個還原 Sprint 可能需要的介面與相容性承諾。

## 已知風險

- 備份成功不等於還原流程已完成；Sprint 04 不提供還原功能。
- 備份若與原資料放在同一實體磁碟，不能防範整顆磁碟故障。
- 預設備份目錄仍位於本機；使用者若需要異地備份，須自行複製完整
  備份目錄。
- metadata 遺失仍會使資料無法解密；每份備份必須包含正確 sidecar。
- 保留清理涉及刪除，必須以路徑限制、格式驗證與成功後清理降低風險。
- Electron 42 將於 2026-10-20 EOL，本 Sprint 不得使升版風險惡化。

- 可讀格式匯出。
- 修改主密碼。
- 閒置自動鎖定。
- 每日／每週／每月分層保留。
