## 適用範圍（v1.1 明確化）

本表管的是**產品與財務領域概念**：財務項目、交易、分類、類型、餘額、淨資產、資料狀態等。

一般技術實作識別字**不在本表管轄範圍**，不需要登記，例如 `Repository`、`Service`、`Draft`、`Snapshot`、`Port`、`Dialog`、`Toast`、`PageSize`。

規則：不得在程式中引入本表沒有的**產品或財務概念**名稱。需要新概念時先更新本表並取得確認。

## 1. 資產與負債

| 中文名 | 程式識別字 | 定義 |
|---|---|---|
| 財務項目 | `FinancialItem` | 使用者持有的一筆資產或負債。含不可用於收付款者（房產、房貸等）。 |
| 方向 | `direction` | 財務項目屬於資產或負債。值為 `asset` / `liability`。 |
| 資產 | `asset` | 增加淨資產的財務項目。 |
| 負債 | `liability` | 減少淨資產的財務項目。 |
| 財務項目類型 | `FinancialItemType` | 內建類型。目前為 `bank_deposit`、`cash`、`property`、`custom_asset`、`credit_card`、`mortgage`、`loan`、`custom_liability`。依 G-01 將新增 `electronic_wallet`。 |
| 自訂類型 | `FinancialItemCustomType` | 使用者自行建立的資產或負債類型。**與「分類」是不同概念。** |
| 資料狀態 | `DataStatus` | 該筆金額的可信度。見第 6 節，**使用者可選與系統寫入的值不同**。 |
| 計入淨資產 | `includeInNetWorth` | 該項目是否納入淨資產計算。 |
| 停用 | `isActive = false` | 保留歷史但不再出現於新增選單。取代刪除。 |
| 總資產 | `totalAssets` | 所有計入淨資產的資產項目金額合計。 |
| 總負債 | `totalLiabilities` | 所有計入淨資產的負債項目金額合計。 |
| 淨資產 | `netWorth` | `總資產 − 總負債`。 |

## 2. 交易

| 中文名 | 程式識別字 | 定義 |
|---|---|---|
| 交易 | `FinancialTransaction` | 一筆已發生的收入、支出、轉帳或信用卡活動。 |
| 交易類型 | `TransactionKind` | `income`、`expense`、`transfer`、`credit_card_purchase`、`credit_card_payment`。**共 5 種，轉帳手續費不是獨立類型（G-02）。** |
| 收入 | `income` | 增加指定資產帳戶，計入當月收入。 |
| 支出 | `expense` | 減少指定資產帳戶，計入當月支出。 |
| 帳戶轉帳 | `transfer` | 自有帳戶間移動。不計收支，淨資產不變。 |
| 信用卡消費 | `credit_card_purchase` | 認列支出並增加信用卡負債，不動銀行存款。 |
| 信用卡繳款 | `credit_card_payment` | 減少付款帳戶資產並同額減少信用卡負債。不再計為支出。 |
| 轉帳手續費 | 無專屬識別字 | **不是交易類型。** 以一筆普通 `expense` 表示（G-02），並透過關聯欄位綁定所屬轉帳（G-05）。 |
| 所屬轉帳 | `parentTransferId`（Sprint 03 新增） | 手續費支出所綁定的轉帳交易。選填。有值時受 G-05 的連動規則約束。 |
| 可收付款帳戶 | `TransactionAccount` | 財務項目中可作為收付款來源或目的者。由財務項目映射而來。 |
| 可收付款帳戶種類 | `TransactionAccountKind` | `cash`、`bank`、`electronic_wallet`、`credit_card`。 |
| 財務時間 | `occurredAt` | 交易實際發生的時間。使用者可修改，不得為未來。 |
| 財務月份 | `financialMonth` | 由財務時間推導的 `YYYY-MM`，決定該交易計入哪個月。時區固定 `Asia/Taipei`。 |
| 餘額影響 | `AccountBalanceEffect` | 一筆交易對某個帳戶造成的增加或減少。 |
| 本月結餘 | `MonthlyTransactionSummary.balance` | `本月收入 − 本月支出`。**不等於淨資產變化。** |
| 期初餘額 | 無專屬欄位 | **不是資料欄位。** 僅為說明用概念，實際就是財務項目的既有金額（G-03）。 |

## 3. 分類

| 中文名 | 程式識別字 | 定義 |
|---|---|---|
| 分類 | `FinancialCategory` | 收入或支出的大分類。目前只有單層。 |
| 分類用途 | `CategoryKind` | `income` / `expense`。 |
| 內建分類 | `isBuiltIn = true` | 系統預設分類，不可刪除。 |
| 移轉後刪除 | `reassignAndDelete` | 已被交易使用的分類要永久刪除時，先把既有交易改為替代分類。 |

## 4. 命名一致性規則

- 「帳戶」一詞**只用於**可收付款帳戶。房產、房貸等一律稱「財務項目」，不稱帳戶。
- 「類型」用於資產／負債（`FinancialItemType`、自訂類型）。
- 「分類」用於收入／支出（`FinancialCategory`）。兩者中文不可互換使用。
- `FinancialItem` → `TransactionAccount` 的轉換只允許發生在單一映射函式內，不得在多處各自判斷。
  目前 infrastructure 有 `mapAccountKind()`，但 renderer 另外用 `account.type === 'bank_deposit' || account.type === 'cash'` 自行判斷可收付款帳戶，違反本條。Sprint 2.5 T-20 處理。

## 5. 已確認決議（2026-07-28）

### G-01　電子支付／電子錢包　→　採 (A)，新增型別

背景：`04_Decision_Log.md` 與 `07_Sprint_02_Plan.md` 都把「電子支付／電子錢包」列為可收付款項目，`TransactionAccountKind` 也有 `electronic_wallet`，但 `FinancialItemType` 沒有對應型別，`mapAccountKind()` 永遠不會回傳它。文件承諾的功能實際做不到，該列舉值是走不到的死路。

決議：新增 `electronic_wallet` 到 `FinancialItemType`，補上映射、中文標籤、新增選單與測試。

**執行歸屬：這是新功能，排入 Sprint 03，不得混入 Sprint 2.5。**

### G-02　轉帳手續費　→　採 (A)，就是普通支出

決議：手續費以一筆普通 `expense` 表示，不成為獨立交易類型。交易類型固定為 5 種。

待辦：修正 `07_Sprint_02_Plan.md` 第 4 節那份寫成 6 項的清單文字，使其與程式一致。（屬文件修正，可在 Sprint 2.5 執行。）

附帶問題「轉帳與手續費是否建立關聯」已於同日決議，見 G-05。

### G-03　期初餘額　→　採 (A)，不進資料模型

決議：期初餘額只是說明用概念，不新增欄位。實際上就是財務項目在第一筆交易之前的既有金額。

**明文限制：未來不得因為文件出現「期初餘額」字樣，就自行新增 `openingBalance` 欄位或表格。** 若日後需要顯示「期初 + 本期變動 = 現在餘額」，必須先更新本表並取得同意。

### G-04　資料狀態　→　採 (A)，使用者只能選兩個

背景：`DataStatus` 的五個值分別來自 `02_Requirements.md` FR-010（實際、推算、手動確認、待確認）與 `01_Product_Vision.md`（更新失敗時標示資料已過期）。兩份文件的概念被併入同一個列舉，這一步當初未經確認。

問題：目前五個值全部放在同一個下拉選單由使用者自選。但 `confirmed`、`pending_confirmation` 是使用者的意思表示，`automatic`、`estimated`、`stale` 是系統的判斷。混在一起會讓使用者手動宣告系統無法驗證的狀態（例如手動選「由系統自動更新」）。且 Sprint 01／02 全為手動輸入，後三者現階段一個都不會真的發生。

決議：

- 五個值全部保留，資料模型不變。
- **使用者可手動選擇的只有 `confirmed` 與 `pending_confirmation`。**
- `automatic`、`estimated`、`stale` 只能由系統寫入，現階段不出現在任何選單。
- 中文文案統一口吻，見第 6 節。

**執行歸屬：這會改變畫面行為，排入 Sprint 03，不得混入 Sprint 2.5。**

### G-05　轉帳手續費關聯　→　採 (A)，獨立支出並綁定父轉帳

問題來源：使用者刪除一筆寫錯的轉帳後，手續費仍留在帳上，必須再做一次相同的刪除動作。實務上手續費是為了那筆轉帳才發生的，不該獨立存活。

決議：手續費維持為一筆獨立的 `expense`（保有自己的分類與流水顯示，不破壞「轉帳不計收支」這條規則），但新增選填關聯欄位 `parentTransferId` 指向所屬轉帳。

**前提修正：手續費並非每次轉帳都有。** 同行轉帳通常免費，網銀多有免費次數，跨行才固定收取。因此手續費欄位一律**選填且預設空白**，不得預設帶入金額。

連動規則（全部必須實作，不得只做刪除）：

1. 刪除轉帳 → 一併刪除其手續費。確認視窗必須寫明將同時刪除的筆數與金額，例如「將同時刪除手續費 TWD 15，共 2 筆」。
2. 刪除手續費 → **不影響**轉帳。連動是單向的。
3. 修改轉帳的轉出帳戶 → 手續費的扣款帳戶跟著改。手續費本來就從轉出帳戶扣。
4. 修改轉帳的財務時間 → 手續費的財務時間跟著改。否則兩筆可能落在不同月份，月度統計會對不上。
5. 修改轉帳金額 → 手續費**不變**。手續費是固定費用，與轉帳金額無關。
6. 手續費的來源帳戶與財務時間不可單獨編輯。可單獨編輯的只有金額、分類與備註。
7. 允許事後補記：對帳時才發現手續費，可為既有轉帳補記一筆並建立關聯。
8. 允許沒有父轉帳的獨立手續費支出（例如帳戶管理費），該情形即為普通支出。

**執行歸屬：Sprint 03。** 這會新增資料欄位、migration 與畫面行為，不得混入 Sprint 2.5。

**同時必須更新的文件（不只術語表）：**

- `02_Requirements.md`：手續費的輸入與連動行為。
- `03_Business_Rules.md`：連動刪除與跟隨規則。
- `07_Sprint_02_Plan.md` US-04 的驗收條件需補充連動說明。

### G-07　「類型／分類」UI 文案修正　→　列為 Sprint 2.5 的明確例外

問題來源：本表第 4 節規定「類型」只用於資產／負債，「分類」只用於收入／支出。但目前畫面仍寫「收入類型」「支出類型」「新增類型」，收支表單的欄位也叫「類型」。

這與 `09_Sprint_02_5_Plan.md`「不得改變任何 UI 文案」直接衝突 —— 遵守本表就必須改文案，遵守該前提就不能改。此矛盾由 Sprint 2.5 開工前的規範審查提出，並依 `AGENTS.md` 停止實作、回報處理。

範圍限定：

## 6. 資料狀態對照表

| 程式值 | 中文名 | 誰可以設定 | 語意 | 現階段是否會出現 |
|---|---|---|---|---|
| `confirmed` | 已確認 | 使用者 | 使用者確認這個金額正確。 | 會 |
| `pending_confirmation` | 待確認 | 使用者 | 使用者尚未確認，需要之後回來處理。 | 會 |
| `automatic` | 自動更新 | 僅系統 | 由自動來源寫入且成功取得最新值。 | 不會（等自動來源上線） |
| `estimated` | 推算 | 僅系統 | 系統推算而非實際取得的金額。 | 不會 |
| `stale` | 可能已過期 | 僅系統 | 自動更新失敗，保留上一筆可信數值。 | 不會 |

文案規則：五個名稱一律使用系統陳述的口吻，不使用第一人稱。現行程式中的「我已確認金額正確」「我之後再確認」屬於待修正文案（Sprint 03）。
